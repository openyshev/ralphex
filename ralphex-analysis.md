## Резюме

`ralphex` — зрелый CLI-оркестратор автономной разработки по Markdown-плану. Он запускает Claude Code или Codex, разбивает работу на отдельные задачи, отслеживает выполнение чекбоксами, делает коммиты, проводит несколько циклов ревью и показывает прогресс в терминале либо web-интерфейсе.

Проект заметно вышел за рамки небольшого скрипта: это Go-приложение примерно на 58 тыс. строк собственного Go-кода, с 129 Go-файлами вне `vendor`, 59 тестовыми файлами, Docker-обвязкой, адаптерами нескольких AI CLI, уведомлениями и браузерными E2E-тестами. Архитектура в целом хорошо декомпозирована и тестопригодна. Главные эксплуатационные риски связаны не с устройством кода, а с самой моделью работы: инструмент передаёт агентам возможность менять код, запускать команды и выполнять git-операции; качество результата поэтому зависит от sandbox-настроек, промптов, внешних CLI и корректности плана.

## Назначение и основной сценарий

Базовый вход — план вида:

```markdown
# Plan: Feature

## Validation Commands
- `go test ./...`

### Task 1: Implement feature
- [ ] Add functionality
- [ ] Add tests
```

Типичный полный запуск проходит так:

1. Выбирает или создаёт план.
2. При необходимости создаёт отдельную ветку или worktree.
3. Находит первую незавершённую секцию `### Task N:` / `### Iteration N:`.
4. Передаёт задачу AI-исполнителю, проверяет сигналы завершения, повторяет при временных ошибках.
5. Выполняет многоагентное внутреннее ревью.
6. Опционально запускает независимое внешнее ревью (`codex`, custom script либо `none`).
7. Выполняет финальное ревью критичных/существенных проблем.
8. Опционально запускает finalize-шаг.
9. Перемещает план в `completed/`, сохраняет журнал и отправляет уведомление.

Поддержаны режимы полного выполнения, только задач, review-only, external-only и интерактивного создания плана. Флаг `--codex` переключает всю основную цепочку на Codex и отключает внешнее Codex-ревью как слабополезную самопроверку той же моделью.

## Архитектура

### Точка входа

`cmd/ralphex/main.go` отвечает за:

- разбор CLI-флагов через `go-flags`;
- загрузку конфигурации и применение CLI overrides;
- определение режима работы;
- проверку наличия Claude/Codex;
- подготовку git-репозитория, ветки или worktree;
- progress log, dashboard и уведомления;
- graceful shutdown и обработку сигналов.

Файл крупный (более 1600 строк), но основная бизнес-логика вынесена в пакеты. Это скорее composition root, хотя дальнейшее разделение повысило бы обозримость.

### Оркестрация

`pkg/processor/runner.go` — координатор верхнего уровня. Он намеренно управляет только последовательностью фаз:

- `TaskPhase`;
- первый `ReviewPhase` и review loop;
- `ExternalReviewPhase`;
- финальный review loop;
- `FinalizePhase`;
- `PlanCreationPhase`.

Конкретная логика фаз находится в `pkg/processor/phase/`. Зависимости передаются через небольшие интерфейсы (`Executor`, `Logger`, `InputCollector`, `GitChecker`), что облегчает unit-тестирование. Это одна из сильнейших частей дизайна.

### Исполнители AI

`pkg/executor/` содержит:

- нативный Claude executor со stream-json;
- нативный Codex executor;
- custom-script executor;
- управление процесс-группами и отменой;
- bounded-буферы диагностик;
- обнаружение completion/error/rate-limit сигналов;
- фильтрацию и нормализацию потокового вывода.

Интеграция учитывает практические проблемы CLI: убийство дочерних процессов, idle/session timeout, Windows-лимит командной строки, повторные попытки, подавление шумного stderr и чтение Codex rollout-файлов.

### Конфигурация и промпты

`pkg/config/` загружает встроенные defaults и накладывает на них глобальную и локальную конфигурацию. В бинарник встраиваются:

- default config;
- prompts;
- определения review agents.

Локальная `.ralphex/` конфигурация может переопределять пользовательскую. Для zero values применяются `*Set`-флаги, позволяющие отличать «не задано» от явно заданных `false`/`0`. Поддерживаются шаблонные переменные и `{{agent:name}}`.

### План

`pkg/plan/` выбирает, парсит и отслеживает Markdown-план. Парсер:

- признаёт только структурные заголовки `Task`/`Iteration`;
- учитывает `[ ]`, `[x]`, `[X]`;
- игнорирует примеры внутри fenced code blocks;
- не присоединяет чекбоксы из посторонних H1/H2-секций к задаче;
- терпим к двум форматам даты в имени файла.

Формат прост и удобен человеку, но синтаксис заголовков является API: локализовать слово `Task` нельзя.

### Git

`pkg/git/` использует внешний git CLI. Сервис инкапсулирует определение веток, diff/hash/fingerprint, коммиты, перемещение плана и worktree-операции. Такой подход проще и предсказуемее Go-библиотек git, но создаёт жёсткую runtime-зависимость от версии и поведения установленного `git`.

### Прогресс и web UI

`pkg/progress/` пишет timestamped-журналы с файловой блокировкой. Завершённые логи архивируются; действует retention на 10 запусков для одного canonical progress-файла.

`pkg/web/` реализует встроенный HTTP-сервер и UI:

- HTML/static assets встроены через `embed`;
- live updates идут через SSE;
- есть single-session и multi-session/watch режимы;
- watcher обнаруживает progress-файлы и умеет повторно активировать сессию после новых записей;
- API отдаёт план и список сессий.

По умолчанию сервер привязан к `127.0.0.1`, что является безопасным default. При публикации наружу отдельной аутентификации в видимой архитектуре нет, поэтому внешний bind следует считать доверенным окружением.

### Вспомогательные интеграции

- уведомления: Telegram, email, Slack, webhook и custom command;
- Docker-обёртка `ralphex-dk.sh`, фактически Python-скрипт;
- адаптеры Codex, Copilot, Gemini, Antigravity, pi и opencode к Claude-совместимому протоколу;
- поддержка Mercurial через `hg2git`;
- shell completions;
- документационный сайт.

## Качество реализации

### Сильные стороны

1. **Хорошее разделение ответственности.** Оркестратор не содержит реализацию фаз; внешние взаимодействия закрыты интерфейсами.
2. **Сильный акцент на тестирование.** 59 Go test-файлов, table-driven tests, mocks, race detector в CI и отдельные Playwright E2E-тесты.
3. **Проработанная отказоустойчивость.** Есть retry policy, rate-limit handling, idle timeout, signal handling, cleanup process groups, break/pause semantics и защита progress logs блокировкой.
4. **Кроссплатформенность.** Unix/Windows-specific реализации вынесены в build-specific файлы.
5. **Безопасные defaults в нескольких важных местах.** Dashboard слушает localhost; GitHub Actions checkout отключает persistence credentials; Claude API key по умолчанию удаляется из дочернего окружения, если пользователь явно не разрешил его сохранить.
6. **Удобство эксплуатации.** Zero-setup defaults, локальные overrides, worktree isolation, progress history, web dashboard и несколько каналов уведомлений.
7. **Документация отражает реальные edge cases.** `CLAUDE.md` подробно фиксирует не только структуру, но и причины нетривиальных решений и инварианты.

### Слабые места и риски

1. **Высокий уровень полномочий AI-исполнителя.** Инструмент предназначен для автономного изменения репозитория, выполнения тестовых команд и коммитов. Ошибка промпта или модели может привести к нежелательным изменениям. Worktree и контейнер уменьшают, но не устраняют риск.
2. **Большая поверхность интеграции.** Claude, Codex, git, Docker, fzf, shell wrappers, уведомления и платформенные различия создают много комбинаций, которые невозможно полностью покрыть unit-тестами.
3. **Хрупкость текстовых протоколов.** Completion-сигналы, Claude stream-json, Codex stderr/rollout и шаблоны агентов зависят от форматов внешних CLI. В коде есть адаптация к текущим особенностям, но upstream-изменения остаются постоянным риском.
4. **Крупные файлы и пакеты.** `cmd/ralphex/main.go`, `pkg/config`, `pkg/processor` и особенно `pkg/web` уже требуют существенного контекста для изменений. Дальнейший рост повысит стоимость сопровождения.
5. **Сложность конфигурационного merge.** Много полей `*Set`, fallback-правил и CLI overrides. Решение функционально оправдано, но добавление каждого нового параметра требует синхронных изменений и тестов в нескольких местах.
6. **Web UI без встроенной аутентификации.** Для localhost это приемлемо; bind на внешний интерфейс потенциально раскрывает планы, ветки и журналы выполнения.
7. **Репозиторий содержит vendored зависимости.** Это обеспечивает воспроизводимость/offline build, но увеличивает объём checkout (2111 tracked files) и требует дисциплины `go mod vendor` при обновлениях.
8. **Несовпадение URL клона и module path.** Клон получен с `openyshev/ralphex`, но `go.mod`, документация и Docker images используют `github.com/umputun/ralphex`. Это нормально для fork, однако релизные пути и ссылки по умолчанию всё ещё ориентированы на upstream.

## Тесты и CI

Основной CI выполняет:

- `go test -race` с atomic coverage;
- тест Docker wrapper;
- тест container init script;
- `golangci-lint` фиксированной версии;
- необязательную отправку покрытия в Coveralls.

Browser E2E запускаются отдельным manual workflow с Playwright. Релизы собираются GoReleaser, Docker images — для amd64 и arm64.

### Что удалось проверить локально

- Репозиторий успешно клонирован, структура и исходники доступны.
- Go-тесты локально не запускались: в окружении отсутствует бинарник `go` (`command not found`).
- Тест Docker wrapper локально не запустился, потому что системный Python — 3.7.9, а скрипт использует современный синтаксис (`list[str]`, walrus operator), требующий более новой версии Python. Это ограничение среды анализа, а не подтверждённый дефект проекта; CI использует актуальный Python на Ubuntu.
- Lint и Playwright E2E по тем же причинам локально не выполнялись.

Следовательно, выводы о качестве основаны на статическом чтении кода, тестов, CI и документации, а не на успешном локальном прогоне suite.

## Рекомендации

1. **Запускать автономные задачи в worktree или контейнере**, особенно для незнакомых репозиториев; не монтировать лишние каталоги и секреты.
2. **Не публиковать dashboard наружу без reverse proxy с аутентификацией и TLS.**
3. **Закреплять версии внешних AI CLI** в воспроизводимой среде и иметь smoke-тест их формата вывода.
4. **Добавить явную матрицу поддерживаемых версий Python/Go/git/Docker** в документацию. Для wrapper стоит проверять версию Python при старте и выдавать понятное сообщение.
5. **Автоматизировать проверку fork-specific метаданных**, если этот fork будет самостоятельно выпускаться: module path, image names, Homebrew/install URLs, funding и ссылки на upstream.
6. **Продолжать дробить крупные composition/UI-файлы** по мере добавления функций, не перенося phase logic обратно в `Runner`.
7. **Для внешнего bind web UI добавить опциональную аутентификацию** либо жёсткое предупреждение при `host != 127.0.0.1/localhost`.
8. **Периодически проводить интеграционные тесты с реальными Claude/Codex CLI**, так как mocks не выявляют изменение внешних JSONL/rollout-протоколов.

## Итоговая оценка

Репозиторий производит впечатление активно сопровождаемого, инженерно зрелого инструмента. Особенно хорошо сделаны границы фаз, тестовые seams, обработка процессов и журналирование. Главная сложность проекта — не базовый алгоритм, а надёжное согласование множества нестабильных внешних CLI и безопасная автономная работа с пользовательским кодом. Для личного и командного использования проект выглядит пригодным, если запускать его в контролируемом окружении и относиться к результатам AI как к изменениям, которые всё равно должны пройти обычные тесты и code review.
